The problem

A lender receives many home loan applications and cannot review every one in depth. If it can see which applicants resemble past borrowers who defaulted, it can spend more review effort where it matters. This project analyses 307,511 historical applications, of which 24,825 (8.07%) defaulted, and builds a tool that estimates the default risk of an applicant.

The tool supports a human reviewer. It does not approve or reject anyone.

How it was built

  • Python and machine learning. Data checks, cleaning, feature engineering and a Gradient Boosting model. On a held-out test set of 61,503 applicants it reaches a ROC-AUC of 0.7529 using complete records. ROC-AUC measures how well a model ranks riskier applicants above safer ones: 0.5 is chance and 1.0 is perfect.
  • SQL (MySQL). The data was loaded into a MySQL database and 12 business questions were answered, such as default rate by credit score, age, occupation and income.
  • Power BI. A dashboard built from the MySQL data, with every figure checked against the SQL results. See the Dashboard page.
  • Flask web app. This website. A small Python backend passes the form values to the saved model. Nothing is retrained.

How a prediction works

  1. You enter the details. Six fields are required and five are optional.
  2. The backend checks them. Every value must be in its allowed range.
  3. A row for the model is built. The model expects 125 input columns. The form fills up to 15 of them: the 11 fields, plus four values calculated from them (age in years, a loan-to-income ratio, an annuity-to-income ratio and an employment flag).
  4. Blanks are filled with typical values. The saved preprocessor fills every other column with typical values from the training data, the same way it handles missing values in the original data.
  5. The model estimates the probability. The saved Gradient Boosting model (100 trees) returns an estimated probability of default.
  6. The result is labelled. The estimate is compared with the 10% review threshold, and a reliability level is set from how many external scores were entered.

Entering details

Required fields must be filled. Optional fields can be left blank, and a typical value is used instead. The training data does not say whether income is yearly or monthly, so enter income, loan amount and loan annuity in the same units. The two example buttons on the Risk Prediction page fill the form with invented applicants, not real people.

Reading the result

The estimated probability

The estimate is the model's probability that an applicant like this defaulted. On the test set it matched real default rates closely: the average estimate was 8.03%, against an actual rate of 8.07%. The table groups test applicants by their estimate and compares it with what actually happened.

The 40% and above group is small, so its figures are less reliable. The model slightly under-estimates risk in the 20% to 40% range.

The review threshold

The review threshold is 10%. An estimate at or above it is labelled "Above the review threshold", which flags the case for a closer look. An estimate below it is labelled "Below the review threshold". Neither label is a decision. A person should make the final decision.

What the 10% threshold did on the test set (61,503 applicants, 4,965 defaulters)
InputApplicants flaggedDefaulters identifiedFlagged who defaulted
All 11 form fields24.5%56.2%18.5%
Complete records (all 125 columns)24.5%57.5%19.0%

The threshold trades one error for another. At 10% the model catches more than half of the defaulters, but it also flags many applicants who would have repaid: most flagged applicants did not default.

Missing external scores

The three external scores are the model's most important inputs, so the result depends on how many you enter. With all three, the result is shown normally. With one or two, it is shown with a warning. With none, no risk label is shown, because in testing the model flagged almost no one. When scores are missing, the model's average estimate is usually lower than the actual 8.07% rate.

Limitations

  • The model shows associations in historical data, not causes. It describes how similar applicants behaved in the past.
  • The model uses gender, which this form does not ask for. The trained model was not changed, so a typical value is used. In some places, lenders may not be allowed to use gender in credit decisions.
  • The model expects 125 input columns and the form collects up to 15 of them. This is why the form is slightly less accurate than complete records (ROC-AUC 0.7418 against 0.7529).
  • Precision is low. At the 10% threshold most flagged applicants did not default.
  • The 10% threshold was the lowest value tested, so lower values were not explored.
  • The data does not describe what the external scores measure, or whether income and annuity are yearly or monthly.
  • The accuracy figures come from the project's own test set. They were not checked on new data.
  • Patterns by age, occupation and education should not be used on their own to approve or reject an applicant.
  • The figures on this page are fixed text and would need updating if the model changed.
  • This site runs on a local development server. It is a portfolio project, not a production system.

Technology

Python (pandas, scikit-learn) for the analysis and model, MySQL for the business analysis, Power BI for the dashboard, and Flask with plain HTML, CSS and JavaScript for this website. The site loads no external libraries.

Questions

Does "above the review threshold" mean the applicant will default?

No. It means the estimate is at or above 10%, so the case is flagged for a closer look. In testing, about 18.5% of applicants flagged this way, using the 11 form fields, actually defaulted. Most did not. A person should make the final decision.

Why does the tool ask for external scores?

They are the model's most important inputs: together they hold about 72% of its measured importance. With fewer scores the estimate is less reliable, and with none the tool shows no risk label.

Why isn't gender asked?

The form does not collect it. The trained model was kept unchanged, and it still uses gender as one of its inputs, so a typical value is filled in. Removing gender from the model would need retraining, and its results would change. In some places, lenders may not be allowed to use gender in credit decisions.

Decision-support tool only. The model was trained on historical data and shows associations, not causes. It uses information that this site does not collect, including gender, which is filled with a typical value. Fields left blank are also filled with typical values. Do not use it as the only basis for a credit decision.
